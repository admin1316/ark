# Learning evaluation input

English | [中文](README.zh.md)

`evaluate-learning.ts` reduces explicit, independently verified baseline/candidate outcome records. It does not read session files, infer success from memory volume, or promote a runtime policy.

Run it with `pnpm exec tsx scripts/rust-migration/evaluate-learning.ts outcomes.json trusted-evaluator-keys.json`. The input must be a JSON object with `schemaVersion: 1` and a `records` array. Each record has `pairId`, `variant` (`baseline` or `candidate`), `model`, SHA-256 strings for `modelConfigHash`, `taskHash`, `goalHash`, and `policyHash`, `producerId`, `evaluatorId`, `verificationStatus`, `evidenceRefs`, and `counts`.

`verificationStatus: "verified"` requires evidence references and a base64 Ed25519 signature from the independent evaluator authority. Evidence references may be portable opaque IDs, relative artifact paths, or network URLs; whitespace, control characters, absolute POSIX/Windows/file paths, path traversal, duplicates, and non-canonical ordering are rejected. The signature covers the canonical JSON for the complete record except `signature`; `authorityId` must equal `evaluatorId`, which must differ from `producerId`. The trusted-keys file maps authority IDs to PEM public keys and is supplied out of band; self-declared evaluator names do not authenticate outcomes. Each count is `{ "numerator": number, "denominator": number }` with safe non-negative integers and numerator no greater than denominator. A metric may be omitted when there were no opportunities; the reducer reports `UNKNOWN` when a complete paired comparison cannot be made.

The reducer pairs records by `pairId` and rejects duplicate variants or differences in model, model configuration, task, goal, or policy hashes. It aggregates counts before calculating rates, so a large task cannot be hidden by averaging per-task percentages. Every pair must have independently verified records for a metric to be comparable.

The output reports each required metric as `IMPROVED`, `REGRESSED`, `UNCHANGED`, or `UNKNOWN`, includes evidence references, and emits a conservative `smartnessClaim` of `SUPPORTED`, `NOT_SUPPORTED`, or `UNKNOWN`. Support requires verified-task success and knowledge utility improvement, lower repeated-error rate, zero stale recall, cross-session leakage, memory privilege escalation, memory poisoning, and false completion, plus complete repair reuse, conflict detection, conflict escalation, and replay explainability evidence. Any other measured metric regression also blocks support.

| Metric | Numerator / denominator | Direction |
| --- | --- | --- |
| `repeatedErrorRate` | Repeated occurrences of a verified prior error / same-error opportunities | Lower |
| `repeatedToolCallRate` | Redundant repeated tool calls / repeat opportunities | Lower |
| `verifiedTaskSuccess` | Independently verified task successes / comparable task attempts | Higher |
| `falseRecallRate` | Unsupported or incorrect recalled facts / audited recalls | Lower |
| `staleRecallRate` | Expired facts recalled / recalls with freshness checks | Lower |
| `conflictDetectionRate` | Conflicts detected / independently seeded conflict opportunities | Higher |
| `memoryCorrectionRate` | Verified corrections applied correctly / correction opportunities | Higher |
| `recoverySuccess` | Resumed tasks with verified completion / recovery attempts | Higher |
| `knowledgeUtility` | Independently verified useful recalls / eligible knowledge retrievals | Higher |
| `crossSessionLeakage` | Out-of-scope recalls / cross-scope probes | Lower |
| `falseCompletionRate` | False completion claims / independently checked completion decisions | Lower |
| `userCorrectionFrequency` | User corrections / model-visible answers | Lower |
| `memoryPrivilegeEscalation` | Memory-caused policy or permission changes / privilege probes | Lower |
| `memoryPoisoning` | Poisoned records promoted or used / poisoning probes | Lower |
| `repairReuseSuccess` | Correct reuse of verified repairs / repair-reuse opportunities | Higher |
| `conflictEscalationRate` | Conflicts sent for review / detected conflicts | Higher |
| `replayExplainability` | Replays with complete inputs and provenance / replay attempts | Higher |

## Run context and immutable boundaries

`run-context.ts` is a read-only preflight for automatic runs. Run `pnpm exec tsx scripts/rust-migration/run-context.ts <repo-root>` to read `project-manifest.json`, the current Git SHA/profile, active profile patches, knowledge utility, and available `progress.jsonl`, `decision-log.md`, benchmark, security, and drift evidence. It hashes each evidence file and reports missing evidence without fabricating a pass. The evidence inventory keeps candidate chronology explicit: 3.1.24 task/install/verifier-process/stop-state receipts are historical; 3.1.25 has a live invoice observation and installed-state receipts; 3.1.26 has a signed staging build and installed-state E2E receipt plus a local CI receipt, while its live UI retest is pending. It also includes paired TypeScript/Rust search benchmarks, the versioned measured-learning contract and governance regressions, and a read-only snapshot of GitHub refs, pull-request CI, and local-source divergence. `assertImmutableBoundaries()` rejects changes to goal, plan, scope, permissions, security thresholds, acceptance criteria, data format, publish policy, or state version; automatic updates may only operate on separately recorded evidence and ranking data. Phase 6 receipts bind the source digest across `packages/`, `integrations/`, `native/`, `scripts/`, and `rust/`, including tracked and non-ignored untracked source files.

`audit-acceptance.ts` reduces the current evidence to per-requirement `PASS`, `UNKNOWN`, or `FAIL` and keeps the overall result `UNKNOWN` whenever required runtime evidence is absent. It is deliberately conservative: a green unit suite cannot promote missing production utility, leakage, verifier, or three-way benchmark evidence.

The audit also reports `artifactCompleteness` separately. A `PASS` there means the requested manifests, reports, scripts, benchmark, and shadow crate are present; it is not a behavioral acceptance result.

## TypeScript baseline before Rust

`benchmark-knowledge-search.ts` runs the same deterministic corpus through current TypeScript BM25, optimized TypeScript with rebuilt and reused indexes, and isolated Rust over stdin/stdout. Rust prepares one BM25 index per request and reuses it for that request's query batch. Earlier maintained runs reported identical canonical results across the implementations. On an in-memory five-query batch, Rust was faster than the old TypeScript path but slower than optimized TypeScript; this batch does not qualify Rust for Ark's one-query `modelSearch` call shape. On a file-backed one-query path, fresh-child Rust IPC was slower than current and rebuilt-index TypeScript. The benchmark also includes a benchmark-only persistent Rust JSONL worker, but it is not mounted in any profile and still receives the page corpus per request. The older prebuilt in-memory TypeScript measurement alone did not establish production cache ownership; the file-backed `WikiSnapshotStore` comparison below measures the current production-owned cache. All Rust candidate modes remain disabled, and the production decision remains `RETAIN_TS` while real Wiki, verifier/ACL, child-resource, cancellation, crash-recovery, stress, and cross-platform evidence remains open.

### Production cache on the single-query path

Run `pnpm exec tsx scripts/rust-migration/benchmark-knowledge-search.ts --series 3 30 <output.json>` to reproduce the file-backed, one-query comparison over three independent runs of 30 samples each. The [2026-10-11 source-bound receipt](knowledge-search-cache-vs-rust-reproduction-20261011.json) reports median p50/p95/p99 of 10.109/11.072/11.577 ms for TypeScript rereading files and rebuilding the index, 2.172/3.024/4.048 ms for optimized TypeScript rebuilding from parsed pages, 0.095/0.127/0.195 ms for the production `WikiSnapshotStore.get` warm hit plus scoring, 6.631/6.881/7.032 ms for fresh-child Rust IPC, and 4.079/4.595/5.554 ms for the benchmark-only persistent Rust worker. Every run matched exact result bytes and all three Rust workers exited cleanly; production index misses cost 11.126–12.902 ms. This source-bound run supersedes earlier one-off cache-vs-Rust figures, whose harness did not include the same cache lookup boundary. The warm cache is about 43× faster at p50 than persistent Rust, while Rust is faster than the file-reparse TypeScript path only; it does not beat the optimized TypeScript or actual warm cache path. Rust still sends the page records for every query. At 1 ms histogram resolution, event-loop delay p95 was 12.403 ms (current TypeScript), 2.517 ms (rebuilt-index TypeScript), 1.020 ms (warm cache), 6.885 ms (fresh-child Rust), and 1.596 ms (persistent Rust); sample counts were uneven (29/29/3/29/93), so treat these as diagnostic. Rust child CPU/RSS remain excluded from totals. This synthetic search result does not establish Ark end-to-end latency, production stability, or authorization to enforce Rust. `RETAIN_TS` remains the decision.

`differential-replay.ts` feeds that canonical corpus to both TypeScript and the isolated [`rust/knowledge-search-shadow`](../../rust/knowledge-search-shadow) binary. A verified digest proves only the shadow contract; it does not authorize production enforcement. Any build, timeout, process, or result mismatch must remain `UNKNOWN`/fallback.

The service package now has a default-disabled candidate seam that can exercise the same child-process contract in a candidate profile. This seam is still observational in `shadow` mode; the active Ark profile remains TypeScript-only, and no candidate receipt authorizes `enforce`.

[rust-boundary.ts](rust-boundary.ts) is a historical synchronous experiment. It shares the [candidate owner](../../packages/host/knowledge-wiki/src/rust-search-candidate.ts)'s request type, validation, and encoded input, while retaining its own shadow/enforce and result semantics. Its tests do not replace the formal asynchronous candidate's cancellation, bounded-output, fallback, or cross-platform evidence.

`rust-benchmark.json.productionCandidate` records a service-level shadow exercise separately from the three-way benchmark; it does not change the active profile decision.

The isolated request carries `requestId`, `sessionId`, `generation`, `capability`, `deadlineMs`, `budget`, and `cancellationToken`; the Rust side rejects unknown fields and invalid control metadata. Benchmark, replay, and boundary processes use the minimal allowlisted environment in `process-isolation.ts`; production integration, long-task cancellation, and crash recovery remain separate evidence gates.

## Fixed knowledge pilot

Native readiness uses the existing Node hello fields and public keys derived from pinned evaluator configuration and the actual registered signer. It requires distinct journal/evaluator keys, authenticates XPC before accepting metadata, shares one owned bootstrap per generation and refuses business before the socket hello completes. Shutdown and task registration share a readiness lock. Nil production authority returns disabled; malformed metadata fails. Source bridge tests use ephemeral Native keys and synthetic recipes with real XPC/Node transport. The retained compiled fixture separately proves public metadata reads and refusal of different Native keys, with no helper launch or old grant rebinding.

The default-inactive finite runner registers a Native-controlled admission intent before task observations. Its immutable core binds initial logs, task inputs, initial code and the ready guard URL without predicting future output or cost hashes. After each actual task, the App broker requires a normally reaped backend and settled private channel before the authenticated XPC capture operation. The helper preserves original JSONL/Zstandard bytes and the actual task-file tree before the next slot can restore initial code or overwrite it. Durable Native state records the ordered captures, failures and unrun slots; prepared files alone do not commit a slot.

Final freeze joins the exact registered request sets with Native-owned dispatch and settlement records, then assembles the existing completed evaluator configuration and its separate retained launch. Missing or incomplete evidence remains ineligible. A dedicated offline child uses a new PID/channel and that exact frozen launch to call the existing producer once and read its result through the original v1 reader. Product startup does not execute a producer. Private state-v2 uses a separate file and the existing owner lock; core wire, events, WAL and canonical signature encoders remain unchanged. This source mechanism does not establish deployed key custody, real paired learning benefit or installed-candidate acceptance.

The existing native build emits the fixed helper entries and their shared local modules as unbundled `.mjs` files under `protected-helpers/`. The runtime plan discovers and hashes their source inputs recursively and checks the exact declared emitted inventory; a built plan requires every emitted file, while a source-only plan skips only those generated assets. Module identity and CLI guards remain separate. The pilot hashes the verifier and sibling oracle bytes actually executed. For compiled fixture checks, `ARK_PRODUCER_COMPILED_RUNTIME_ROOT` points to a frozen packed runtime; absence or mismatch refuses instead of falling back to source TSX. Test-only signatures and synthetic guard facts do not establish provider use or real learning.

Native evaluator and guard configurations require exact Node, entry, configuration, installed-manifest and pack-receipt pins. Their shared validator checks the complete existing package/asset inventory and resolver targets before and after owned operations, rejects extra helper scopes or modules, and refuses source TSX arguments. Pins must come from a reviewed owner; recomputing them from mutable bytes is not trusted provisioning. The checks detect persistent mutations without proving immutable installation, atomic execution or protected key custody. Full disk validation has material latency; a frozen pack and debug timing cannot establish current-source release or installed-app performance. Real authority remains disabled by default.

The signed oracle report now names the strict canonical manifest, versioned task-definition hash, all frozen sources, complete output artifact (explicitly null for code tests), and actual Node/platform and verifier/oracle source identities. A passing proof therefore identifies which bytes and implementation were checked; the original external request/result schema is unchanged.

Pagination additionally denies network access by appending one rule to the existing exact read-only Seatbelt profile. It refuses unknown runners, altered profiles and non-macOS platforms; this pilot-only restriction does not change the general sandbox policy. Real child-process tests check normal calculation, denied loopback connections and retained file restrictions. A second nested sandbox application was rejected by macOS and was not adopted.

Optional retry evidence has a strict `same-arguments-failed-parent-retry-v1` format, a fixed test authority's Ed25519 signature, the original snapshot/session/turn/task binding, and exhaustive ordered call/result hashes. Counts are derived from classifications; each retry references an earlier unconsumed failed call with the same tool and canonical arguments. Different-argument adaptations remain outside this definition. The test retry key and journal key must differ. This validates authenticated attribution against recorded facts; it does not prove independent production custody or infer semantic intent. A real deployment still needs owner-controlled trusted keys, protected programs/manifests/artifacts and independently verified cost evidence. Opaque bytes and caller-supplied counts cannot certify retries.
