# Agent Note: 共享运行时 JSON 哈希

Status: implemented

[English](2026-10-11-shared-runtime-json-hash.md) | 中文

## 问题

运行时构建计划和已安装闭包校验分别实现同一套 JSON 内容清单哈希。维护独立副本会使键排序或序列化产生差异，即使清单契约没有改变。

## 决策

[构建计划](../../../../integrations/jiuzhang/src/runtime-plan.mjs)导入[运行时闭包所有者](../../../../integrations/jiuzhang/src/runtime-closure.mjs)已有的 `jsonSha256`。该实现使用现有比较方式排序对象键、保留数组顺序，以两空格缩进及末尾换行序列化，并对完整 UTF-8 字节求哈希。

内容遍历保留各自策略：运行时闭包拒绝硬链接并忽略 Finder 元数据，计划则记录源码内容。共享哈希不合并这些边界，也不改变源码身份绑定的输入。

闭包 CLI 启动校验时不使用顶层 await，使模块先完成导出求值，再动态加载源码计划。这样计划导入共享函数时，不会等待正在等待计划的校验模块。子进程契约验证绑定计划一致时通过，源码计划变化时仍以退出码 2 拒绝。

## 已考虑的替代方案

**保留两份实现。** 内容清单需要统一哈希规则，闭包已经导出该函数。

**新增工具模块。** 现有所有者同时服务构建和运行时消费者，另加文件或依赖不会提供新的契约。

**同时共享目录遍历。** 两者的准入和失败策略不同，哈希相等不能证明遍历策略等价。

## 后果

计划删除本地排序及 JSON 哈希函数。导入不增加新的包、文件写入或进程启动。差分比较覆盖有限 JSON 和文件、链接清单对象的完整序列化字节及摘要；现有运行时计划和闭包测试保留源码绑定、包边界及篡改拒绝检查。即使内容哈希规则未变，源码修改仍会改变绑定的源码身份。这些检查不代表已安装候选或发布验收通过。
