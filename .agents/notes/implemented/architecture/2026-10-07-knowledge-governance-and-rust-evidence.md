# Agent Note: Governed knowledge events and evidence-gated Rust selection

Status: implemented

English | [中文](2026-10-07-knowledge-governance-and-rust-evidence.zh.md)

## Problem

The active Ark source stores Wiki candidates, reviews, verifier receipts, and utility counters, but model-visible retrieval and injection need durable provenance, scope checks, expiry, conflict handling, and replay. The repository also needs a defensible Rust decision that does not replace a working TypeScript kernel without end-to-end evidence.

## Decision

Knowledge records use explicit provenance, trust, authority, evidence, verification, scope, ACL, expiry, conflict, and utility fields. A hash-chained project journal records observation, candidacy, verification, rejection, retrieval, injection, conflict, expiry, promotion, and rollback. Candidate lifecycle events carry the complete record; promotion requires the existing independent verifier and review transaction. Model-facing Wiki tools append `knowledge/retrieved` and `knowledge/injected` session events containing call identity, scope, result hashes, and replayable JSON values. Unverified, stale, conflicting, out-of-scope, ACL-denied, or low-confidence records fail closed.

Within a complete event stream, `readKnowledgeEventLog` and `replayKnowledgeEvents` share one authorization-consumption check. It rejects repeated canonicalized verification or promotion semantics independently of proof encoding, and permits each promotion trial hash only once, including re-signed payloads. Event wire bytes and public replay-state fields stay unchanged. The single-event `applyKnowledgeEvent` fold has no complete authorization history. Previously unconsumed old proofs and rollback or replacement of the entire journal still require trusted-owner freshness state; complete-stream deduplication is not complete revocation-replay protection.

A verified record with at least three retrievals and no positive utility is expired in the event journal before the next model-facing lookup.

When `ownedStageExecutor` is enabled, deadline or owner cancellation aborts the stage and waits for all actual in-process Worker termination joins registered to that stage signal. `Promise.allSettled` lets every join finish before any join failure is propagated; an unsettled join can keep the operation pending. This proves quiescence only for registered Workers. Pre-worker connection resolution and opaque provider termination remain unproven, although the post-resolution signal check prevents a late Worker from starting.

The complete utility JSON projection is UTF-8 byte-counted against the existing 5 MiB consumer limit before its lifecycle writes. Repair begins with non-persisting expiry replay and builds the final projection; only after it fits does the owner persist expiry and revalidate the authenticated current source. It then appends `knowledge/rejected` before corrected `knowledge/injected`, replays the authenticated journal, and checks source identity, rejected/downgraded state, and all four utility counters before writing the utility file or publishing Candidate and Review. A failed first append cannot guarantee that revocation occurred and stops later writes. If the corrected-feedback append fails, the durable rejection remains and the source is refused, while utility, Candidate, and Review stay unwritten. External loss or damage of the journal is outside this guarantee. This ordering does not make event batches or the related files atomic.

The `.llm-wiki/review.json` owner shares an 8 MiB bound between readers and writers and checks the complete formatted JSON array as UTF-8, including JSON escaping and its final newline. Ingest, research, session-summary, correction-repair, and captioned-image producers serialize every possible successful subset and same-path content variant before the first Candidate, governance, or Review publication; commit rechecks exact review-file bytes, the confined Candidate path and bytes, source identity, and current governance decision. A regular in-project source file is bound by its current bytes; an external, virtual, or absent source path binds only its path string, and an unspecified source uses the fixed `unknown-source` marker. Research's `research:${topic}` label binds the request identity, not fetched facts. A source, media, or other raw prerequisite may already have been written, and later file or journal failures can leave partial publication. The plan preserves legacy duplicate IDs and updates only the first matching row, as existing consumers do. This is neither a cross-process lock nor a multi-file transaction. Wiki pages and utility projections retain their 5 MiB bound, promotion WALs retain 8 MiB, and captioned image sources retain 16 MiB with byte comparisons after captioning and after review preflight.

The verification writer awaits authentication of its complete lifecycle payload before publishing Review and governance projections. It captures the Review's original bytes with its parsed rows, reuses the Candidate snapshot for the signed record, and revalidates receipt identity and proof before checking current receipt, Candidate, Review, source/build identity, and event-log bytes after authority callbacks. Cancellation and project changes during signing refuse publication. A refused or invalid seal publishes no projections. The publication check preserves the existing event format; it is not a multi-file transaction or a cross-process lock. Later projection I/O failures remain errors with possible partial audit state, while model access still requires an authenticated lifecycle event. Test-authority refusal, deferred-signature state changes, valid replay, and real Loader tool calls pin these rules without claiming protected production key ownership.

The `knowledge-wiki/src/measured-trial.ts` reader validates signed, content-addressed proposal, authorization, preregistration, paired-use, and trial artifacts. The current source wires it through an optional launcher-owned `knowledgeWikiMeasuredTrialReader`, an additive `recordCandidateMeasuredTrial` RPC, review commit, and crash recovery. Commit applies only the exact target bytes authenticated by the trial receipt. Jiuzhang now maps an exact launcher-only JSON config with separate Ed25519 SPKI public keys and a bounded content-addressed file store; the active environment still supplies no trusted authority values or paired evidence, so production canonical actions remain fail-closed until those inputs are provisioned and independently reviewed.

The semantic owner rejects missing Candidate and target fields when rebuilding the exact canonical-action request. Measured bindings derive their required fields from that matched authenticated request instead of repeating checks on the private parsed review. The transaction owner freezes each flat expected binding before giving it to the reader during registration, authorization, or recovery, so a reader cannot change the values it must satisfy. Promote derives verified absence once; mutable target presence and bytes, receipt validity, eligibility, Candidate bytes, and archive collisions remain independently revalidated at their access and commit points.

`knowledgeWiki/reviews` derives Candidate actions through the existing measured-authorization owner on each read. Projection and commit share the same governed-event check for the existing expired, conflict, scope-denied and ACL-denied reasons; legacy rows without a projection and unverified or rejected states retain the existing review policy. Current semantic receipts, Candidate bytes, target state, independent trial binding and positive utility must authenticate before the bound action is returned; stored action names and labels are not trusted. Missing authorities, invalid evidence and resolved Candidates expose only Archive. The projection does not write Review, Candidate, Canonical or lifecycle files; authority and uncaught I/O errors still reject the call. Resolution independently revalidates before applying an action, so listing an option does not reserve its eligibility or replace commit checks.

Receipt field validation applies even after signature authentication. Artifact hashes and proposal bindings are checked at their owning parsers; a unique, nonempty preregistration and exact baseline/candidate order establish complete pairs. Review commit and crash recovery independently revalidate mutable target state before writing. The transaction owner rechecks current trial eligibility after signing and before persisting its journal. Successful Canonical recovery consumes the required trial established by that validation; Archive remains a separate action, and an authentic semantic-only legacy journal still rolls back. The final validated return and Canonical event projection have no duplicate missing-trial fallback. Seal-refusal tests require reaching the signer instead of passing through an earlier missing-trial refusal.

Evaluator signatures authenticate use receipts and referenced artifact hashes. Every use names a separate journal-owner attestation first in its existing evidence references; the configured journal key authenticates its versioned factual binding and nonempty journal byte snapshot. The factual hash excludes evaluator-owned outcomes/signatures and the subsequently added evidence references, so signing has no circular artifact dependency. Distinct ids and keys preserve the producer/evaluator boundary. This authenticates a signer binding; coherent real session capture, independently checked task results, protected signing ownership, and correctly reused knowledge require their own evidence.

The launcher-only `knowledgeVerifierConfig` contains the verifier authority id, executable, Ed25519 public key, source identity, and optional arguments and timeout; it rejects `privateKey`. With a nonempty config, the Wiki resolves `knowledgeWikiVerifierAuthority` from Context and requires a matching authority id and typed `sealPromotion` method. The external verifier authority captures its validated command, source identity, and deadline at creation, copies its argument array, and retains the parsed public key, bound sealer, and shared managed subprocess owner rather than the caller's mutable options. Verification results and delegated seals are checked with the configured public key; a different valid public key can be accepted at construction but its first seal is rejected if it does not match the sealer. The configured timeout governs verifier subprocess execution only. A project-generation controller aborts pending verification and promotion signing on workspace switch, removal of the current workspace, or disposal; verification combines the caller signal with that generation. The adapter forwards this signal to the typed signing owner without adding a signing deadline. Promotion-event, WAL, and recovery awaits retain their generation and current-state checks. A cooperative owner stops and awaits its process tree before settling; a signal-ignoring owner can remain pending, and synchronous Wiki disposal does not itself await those calls. Signing accepts closed, schema-checked verification-event, promotion-event, or promotion-WAL operations and encodes their existing canonical bytes; it rejects arbitrary strings and mismatched operation or authority context. Knowledge-record semantics reuse the governance validator. That owner requires `lastVerifiedAt` and `expiresAt` to be null or JavaScript strings before applying its existing `Date.parse` policy, and accepts an omitted `claimKey` while requiring a supplied value to be a JavaScript string. This prevents implicit array-to-string date parsing and keeps strict claim-key comparison aligned with its declared type. The encoder's trust and WAL-role allowlists likewise require JavaScript strings before exact membership checks, without coercion. Promotion and authorized recovery obtain event signatures before journal operations, compare current bound state after signing, and commit without a later asynchronous signer call. Typed delegation does not isolate production keys or establish protected OS custody. Reassigning launcher options or editing their argument array cannot redirect verification or change receipt and promotion identity. Real managed-process regressions pin command, argument, deadline, and identity stability; signed fixtures prove configuration binding, not independently verified knowledge reuse.

Promotion transactions apply the signed WAL operations in order, synchronize their parent directories, assert the complete after-state, append the lifecycle event, and synchronize the event file and parent before writing the `committed` marker. Event lookup uses type, candidate knowledge id, and candidate hash to find possible matches, rejects duplicates, and then compares scope and the full semantic payload; for promoted events only the authority-specific seal proof is excluded from that comparison. The lookup tuple alone is not a deduplication rule. Recovery replays a prepared journal idempotently and ensures its lifecycle event before committing. For a committed journal with a complete matching event, recovery synchronizes that event and skips the old file after-state check, preserving later legal changes. If the event is missing, recovery reauthenticates the journal and verifies every current operation after-state, then appends only the missing event; it does not replay or roll back the completed files. Archive and Skip rejection payloads come from the signed governance append, and `appliedPath` must match the actual candidate-archive operation. Conflicting events, invalid authority, or divergent bytes fail closed. I/O errors may leave a prepared journal with visible operation or event bytes, or return after rename with a committed marker visible; rollback is not guaranteed for every failed call. These transaction checks do not establish settled asynchronous signer ownership, protected OS key custody, or real paired-use utility.

Before the first persistent transaction write, the writer bounds all formatted WAL marker forms as UTF-8 against the recovery reader's existing 8 MiB ceiling. The check includes every operation's `before` and `after` strings, duplicated Candidate and archive content, cumulative Review and governance snapshots, the seal and metadata, and JSON escaping; a file within its own read limit therefore does not guarantee that its enclosing WAL fits. This preserves recovery capacity rather than adding large-input support, and recovery continues to refuse older WAL files already above 8 MiB.

Knowledge event readers and appenders share a 64 MiB whole-file UTF-8 limit. Before opening or writing, the append owner checks the exact serialized JSONL line against the current file size, then rechecks after validating the path and opened inode; a crossing append is refused without appending bytes. The writer does not truncate, compact, or rotate an already oversized log, which the bounded reader continues to reject. Callers must serialize writes to the same path: the owner holds no cross-process lock, and callers that append a batch of events may leave earlier valid rows visible when a later row is refused. This finite limit does not provide unbounded history or an atomic multi-event transaction.

The correction RPC validates project, workspace, and session field types at its untrusted input boundary before path resolution or session reads. The input owner normalizes the captured rule and refuses an empty result before the session read; the private authorizer consumes that validated value while Candidate publication preserves the original trimmed text. The existing writer captures its flat proposal and complete access context in operation-owned frozen objects before validating them; an asynchronous query therefore authorizes and records the same captured rule and session even when the caller edits its original objects. Public-entry and real Loader regressions check the original session provenance, original Candidate text, unchanged source, and denied Candidate model reads. Refused input leaves both the source and Candidate state unchanged. Governance replay uses one missing-record decision for the parsed current/fallback record; journal append, review commit, and recovery retain their separate mutable-state checks.

The correction authorization scan binds the matching tool call to the latest logged turn header, so an earlier human rule cannot authorize a later turn, including a reused turn number or malformed latest header. An unreadable latest direct human body refuses authorization rather than borrowing an earlier rule; the real session-query provider already rejects malformed bodies at complete-log replay. The writer revalidates registration, confinement, current admission, identity, and content after the asynchronous session read. The real Loader composition uses the session store and session-query provider to check that malformed-log, stale-turn, and concurrent-file-edit refusals preserve the lifecycle journal and absent Candidate; an exact current-turn rule still stages an untrusted Candidate and blocks the old source. Source regressions also cover concurrent revocation, signed replacement, deletion, and workspace removal. Signed test-authority fixtures represent prior authenticated state only and do not count as positive learning evidence.

Full source reads purge expired process-local capabilities, refresh the session-bound entry, and evict the oldest entry at the fixed 256-entry limit. A positive capacity and the private synchronous Map guarantee a first key at eviction, so the owner deletes it directly. Public-entry regressions check expired and evicted sessions are refused without writes, a refreshed session retains its permission, and deadline expiry is journaled once before returning cached search results. These checks establish bounded authorization behavior, not memory or speed gains.

The assembled ACP repair snapshot inserts the real Wiki service in both live and replay patches and uses the launcher's home-path helper. A correction proposed without reading its verified source is refused, and the independent workspace oracle remains empty. Its authored replay verifies composition and the refusal boundary; it does not establish model learning, positive verification, or cross-conversation reuse. Journal interleaving tests preserve the original bytes and reject symlink, hard-link, directory, and inspection-denial replacements after the complete log read.

Unsigned admission events cannot label their records verified or canonical. The authenticated verification event supplies the complete matching record, owns provenance, and retains Candidate lifecycle until measured promotion. Model content gates bind current page bytes to the latest authenticated promotion hash; the final page read and repair source read repeat the comparison before returning content or authorizing a correction. The Loader-composed Wiki tool refuses a self-certified record without injecting it, and a real file replacement between the content check and final read is rejected without recording a retrieval. These regressions establish trust boundaries, not positive learning or live candidate acceptance.

The checkout includes a default-disabled isolated Rust search shadow. Its prepared index retains document token counts, term frequencies, and title-term membership; it consumes token vectors and derives document frequency from unique frequency-map keys without changing ranking. The existing serde formatter uses [Ryū-js](https://github.com/boa-dev/ryu-js) for ECMAScript-compatible score bytes in both results and their digest. Parent validation reuses the TypeScript tokenizer and checks the child's existing UTF-8 and token limits before spawn; digest comparison remains exact. The [historical synchronous boundary](../../../../scripts/rust-migration/rust-boundary.ts) shares the [candidate owner](../../../../packages/host/knowledge-wiki/src/rust-search-candidate.ts)'s request type, validation, and encoded input. Its modes and output remain experiment-specific; its tests do not replace asynchronous cancellation, bounded-output, fallback, or platform evidence. Knowledge search, graph derivation, session persistence, and subprocess supervision remain TypeScript or existing native C in the active runtime. The Rust candidate matrix requires current TypeScript, optimized TypeScript, and real N-API or IPC Rust comparisons with differential replay, cancellation, recovery, packaging, and platform evidence before enforce mode.

Number-format compatibility is separate from score equivalence. A real-process replay also exposed platform `ln` versus Node `Math.log` rounding differences; an isolated maintained `libm` probe did not reproduce the Node bits and was not adopted. Complete score and digest comparison stays strict, the candidate stays disabled, and platform/corpus matching remains an open gate.

Learning claims use paired baseline/candidate outcome records with the same model, configuration, task, goal, and policy hashes. Missing opportunities or independent verification produce `UNKNOWN`; memory volume, model-call count, or Rust line count cannot establish improvement.

A strict manifest binds the request, source snapshots, and protected tests; arbitrary commands and broader prose rules do not receive a passing result. Actual-use capture reuses core session projection, stream assembly, and persistence decoding without editing original logs. Test-key signatures and historical replay establish those mechanisms, while protected authority ownership, actual paired benefit, and real candidate acceptance remain separate requirements.

## Alternatives considered

The fixed pilot's signed oracle artifacts explicitly bind its canonical manifest, versioned task contract, frozen inputs and whole output, plus runtime and oracle/verifier source identities. Pagination extends the existing exact read-only Seatbelt profile with kernel network denial and refuses unsupported platforms or changed runners; it does not weaken or broaden the general sandbox. Real loopback and file-denial tests complement normal computation. Retry counts use complete signed, snapshot-bound call/result classifications with an earlier failed same-tool/same-arguments parent, no duplicate parent consumption, and distinct test retry/journal keys. Changed-argument adaptations and missing evidence remain outside that definition. Test signatures authenticate these bindings, not independent production ownership or real learning utility; costs and trusted key custody still require separate evidence.

- **Unlogged Wiki recall:** rejected because model-visible input must be reconstructable from the session event log.
- **Automatic promotion from utility or model output:** rejected because low-trust and unverified content cannot change runtime policy or canonical knowledge.
- **Rust-first migration:** rejected because Rust has not implemented the complete production search contract, and mature TypeScript/native owners already provide cancellation and recovery.
- **Digest tolerance or a hand-written number formatter:** rejected because numeric equality does not authenticate result bytes; the maintained ECMAScript formatter supplies the needed boundary behavior without another decimal conversion implementation.
- **A single aggregate score:** rejected because explicit rates and zero-leakage requirements must remain independently inspectable.

## Consequences

The Wiki event journal is auditable and replayable, while canonical files remain protected by the existing review and verifier WAL. Session-event additions do not change the session format version. Tool results without a calling session are still usable for non-agent callers, but no model-visible agent call can bypass session event recording. Rust enforcement stays deferred until a concrete candidate has registered corpus, boundary, and three-way evidence.
